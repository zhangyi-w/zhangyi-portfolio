How I work an AI build

How I scope an AI build
The first call decides everything downstream: which AI primitive matches the problem. RAG when grounded knowledge matters; agents when multi-step tool use matters; embedding rank when semantic similarity is the whole game; classical ML when LLM tax isn't justified. I pick by the shape of the problem, not by what's on trend. And I define the eval rubric before writing a line of pipeline code — if you can't say what "good" looks like up front, you can't tell whether the system actually got there.
Proves — primitive selection by problem shape, eval-first rigor, not hype-driven choices
How I architect for production
The two or three early calls — chunking strategy, cache layer, retrieval shape, eval rubric — decide whether the system holds up at scale or falls over at 10× load. Architecture-first, then ship the smallest production-shaped thing that can be measured. The cookbook is a starting line, not a finish line. Most production failures I've seen came from teams accepting the default chunking, default retrieval, default eval — and discovering at scale that defaults aren't tuned to their problem.
Proves — architecture-first AI builds, defensible at production load, with the right early calls
How I evaluate AI
Faithfulness, latency, cost, hallucination rate — measured on real evals built around the actual user task, not on benchmarks of convenience. If faithfulness drops below target, that's a signal to re-architect, not retry. Vibes-based "it feels good in demo" is how production-AI systems become liabilities at scale. The eval is the contract; the system is what either holds or breaks against it.
Proves — production-AI evaluation discipline, the metrics enterprises actually pay for
